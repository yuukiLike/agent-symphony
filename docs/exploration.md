# 探索方向

Agent Symphony 想把执行现象变成可以听见、重放和对照的音乐。它也可以只是一个有趣的小项目，不预设必须成为完整的监控系统。

本文记录当前讨论的结论与待验证的假设，不是已经实现的规格。返回 [项目首页](../readme.md)，或查看 [事件来源](events.md)。

## 2026-09-21：本轮选择

用户选择「执行发声」：动作、等待和并行直接变成可辨认的声音，像听一台机器运转。声音的节奏跟随实际执行；当前探索以动作的听觉身份、开始与返回、间隔和交错为中心。任务旋律的成长、音乐叙事和演奏已有曲目不作为本轮主线。

具体候选规则与试听实验见 [直接听见执行](designs/direct-execution-sound.md)。方向已选择，音色的听觉辨识度仍待用户试听；下文的旧有声音映射继续作为候选材料。

随后用户明确：工具保持旁观，清楚记录完整执行过程，提供清楚的 session 切换，并能指定 skill 进行调查。Hooks、tools、MCP 是例子，不限制事件模型的范围。新的过程展示、调查与声音联动提案见 [Session 与 Skill 调查](designs/session-investigation.md)。

进一步要求所有 hook 均可指定声音，并先研究 Codex、DeepSeek Harness（dsh）、Claude Code、Pi 的配置。本轮已完成 [四平台配置与事件比较](research/agent-config-comparison.md) 和相应的 [观察与声音配置设计](designs/observation-and-sound-config.md)。原生名称与证据差异保留，声音设置共用；配置可保存与运行可采集分别呈现。随后按用户要求先实现 dsh，现已完成本地记录器、调查界面、配声回放和真实宿主隔离联调，具体范围见 [项目首页](../readme.md) 与 [验证记录](verification.md)。

## 已确认的方向

- 关注执行过程，不只在成功或失败时播放提示音。
- 声音密度、重复与重叠本身就可以传达现象。
- 错误应当可以被听见，但不另建主动告警机制。
- 面向单 Agent，也探索多个任务与多个 Agent 同时运行的情况。
- 记录与重放有助于理解 Agent 流程，也有助于试验声音设计。
- 同一任务的多次执行可以对照，但只呈现差异，不自动解释原因或评价质量。

## 声音要表达什么

听到一段熟悉的短乐句越来越密，可以让人注意到某类操作更频繁了。几个声部交替出现，可以让人感到不同 Agent 正在轮流活动。一次失败后的再调用，可以形成可辨认的变化与重复。

这些是听觉设计假设，需要实际试听，不能仅凭文字映射就宣称成立。

| 可尝试的声音维度 | 想表达的现象 | 需要验证的地方 |
| --- | --- | --- |
| 音色、音区或声部 | 不同任务、Agent 或操作类别 | 身份太多时还能否分辨 |
| 短音型或乐句 | 一类活动或一个可识别操作 | 相似操作会不会听起来完全一样 |
| 密度与间隔 | 一段时间内的活动频率、等待 | 音乐编排是否掩盖了原始节奏 |
| 多个声部重叠 | 同时发生的活动 | 能否听出并行，而非只觉得吵 |
| 音色或音程变化 | 明确报告的错误、中断等结果 | 能否辨认，同时不过度打扰 |

不把高频事件直接等同于高音量。音量、静音与声音密度应可控；如何在好听和保留执行特征之间取舍，留给试听决定。

## 多 Agent 不只是多放几种乐器

需要区分不同任务，以及同一任务中的主 Agent 和子 Agent。可能的做法是让任务拥有稳定的声音主题，让子 Agent 在同一组音色中拥有各自声部，但暂不固定映射规则。

创建子 Agent、交接、等待子 Agent 返回，与真正同时执行是不同现象。只有事件来源提供足够的身份、关联和时间信息，才能可靠地表现这些关系。

Agent 数量增加后，可以试验分组、选择性静音或减少细节。任何聚合都可能丢失信息，需要让使用者知道自己听到的是哪一层。

## 对照同一任务的多次执行

我们想呈现的是这样的现象：

- 这次比上次多了三次搜索，对应乐句也多了三次。
- 中间同一类操作反复出现，短乐句连续重现。
- 某次调用等待更久，两段声音之间的间隔更长。
- 原本依次出现的活动，这次有一部分重叠了。

这些都是示例，不是实际测量结果，也不自动意味着更好、更差或陷入循环。

对照时应尽量固定声音映射、事件筛选规则、播放速度与时间基准，并保留相应配置。重放同一段记录，不应因为随机配乐而制造新的差异。

“相同”需要先说清楚比较什么：调用次数、类型与顺序、参数、结果、时间，还是最终产物。工具名称相同不代表操作相同；最终结果相同也不代表执行路径相同。

音乐只是观察入口。相同的声音不能证明完整执行相同，听到差异也不能单凭声音确定原因。需要精确核对时，回到事件记录。

## 记录事实，保留未知

适配时应区分三件事：来源直接报告的事实、根据事实计算出的特征，以及目前不知道的状态。例如，“最近十秒有五次调用”可以计算；“这五次调用毫无进展”不是同一回事。

几个容易混淆的边界：

- 没有新事件，可能是等待、静默计算、连接问题或采集缺失，不能直接叫作卡住。
- 收到开始却没有结束，只能说明结果尚未被观察到。
- 一轮回复结束，不等于整个任务成功，更不等于结果正确。
- 重复调用不一定是重试，也可能是正常批处理。
- 输出流的分块频率受传输方式影响，不等于 Agent 的动作频率。

声音生成不应改变 Agent 的决策或阻塞工具执行。实现时需验证这一点，不能因为接上 hook 就默认没有影响。

记录范围也需要克制。音频通常只需要事件类型、身份、时间与状态，不必默认保存完整提示词、参数或工具输出。若为精确对照保留更多内容，需要先考虑隐私与脱敏；真实执行记录不应直接提交进仓库。

## 第一次实验

建议先验证一件事：一小段执行过程，能不能被听出结构。

1. 从一个明确的事件来源取得一小段记录，覆盖工具调用、等待、明确错误与结束。尚未接入时可以使用模拟事件，但必须标明模拟。
2. 用少量固定音色和短音型播放，不先追求复杂作曲。
3. 在同一映射下，对照调用变密、乐句重复、等待拉长的几段记录。
4. 先听声音，再核对事件，记录听到了什么、误听了什么、哪里开始疲劳。

先确认“听起来有趣且能感知一些现象”，再决定实时接入、多 Agent 编排与精确对照值得做多深。这是建议的实验顺序，尚未开始实施。

## 暂不承诺

- 全平台、全事件覆盖，或读取 Agent 的全部内部思考。
- 自动诊断卡住、循环、效率低下，或评价任务结果。
- 声音与完整执行记录一一对应。
- 已存在可安装的 npm 包、稳定 API 或可用演示。

首个接入平台、事件记录格式、声音引擎、播放位置，以及第一版做到实时还是重放，都留待下一次小实验决定。
